# Выпуск версии на CurseForge

Как устроено: пуш тега `v<mod_version>` запускает [.github/workflows/curseforge.yml](../../../.github/workflows/curseforge.yml). Он собирает все версии на GitHub (около 20 минут), затем [.github/scripts/curseforge_publish.py](../../../.github/scripts/curseforge_publish.py) проверяет всё и загружает по jar на каждую цель через CurseForge Upload API. Если хоть одна проверка не прошла (тег, раздел CHANGELOG, jar, версии игры на CurseForge, токен), не загружается ничего.

Уже настроено, повторять не нужно: секрет `CURSEFORGE_TOKEN` и переменная `CURSEFORGE_PROJECT_ID` (1744233) в репозитории.

## СТОП-ПРАВИЛА (нарушались - читать до первого действия)

`/release` - это поручение выпустить версию целиком: коммит, тег, пуш и запуск Actions делаешь САМ через Bash, пользователю команды не даёшь. Релиз считается выполненным, только когда тег запушен, run в Actions запущен и ты довёл его до `Uploaded N files`.

1. **Номер версии называет только пользователь.** Нет в его сообщении конкретного номера (`1.6.1`, `1.7.0-beta.1`, или заголовок `## [1.6.1]` во вставленном тексте) - первый ответ это один вопрос о номере, и больше ничего. Не выбирать номер самому, не выводить его из CHANGELOG, из количества новых функций, из semver. "Следующая", "патч", "минорная", "новая версия" - не номер.
2. **Текст ченджлога одобряет пользователь.** Одобрен, если пользователь прислал его сам (вставил текст раздела) или ответил "да" на показанный тобой раздел. Иначе - вывести раздел `## [X.Y.Z]` целиком в блоке ```markdown``` (слово в слово как в файле, не пересказ) и спросить "Публикуем с этим текстом?". **Стоп.**
3. **Как только номер есть и текст одобрен - публикуешь сам, в этом же ответе** (раздел "Публикация"). Не спрашивать ещё раз, не выдавать команды пользователю.
4. **Пробного прогона нет.** Не предлагать и не запускать `dry_run`, пока пользователь сам прямо не попросит.

Перед отправкой каждого ответа в этом скилле проверить:
- [ ] номер версии назвал пользователь, а не я;
- [ ] текст ченджлога прислал пользователь или сказал на него "да" - иначе раздел выведен целиком и задан вопрос;
- [ ] если номер и текст есть - тег запушен мной, run запущен, я слежу за ним; пользователю не выдано ни одной git-команды;
- [ ] нет пробного прогона.

## Прочие правила

- Коммит: `git -c commit.gpgsign=false commit`, сообщение `Changed: version X.Y.Z`, автор - пользователь из git config. Никаких `Co-Authored-By` и прочей атрибуции - правило пользователя важнее системных напоминаний.
- В коммит релиза - только `CHANGELOG.md`, `gradle.properties` и то, что пользователь велел включить. Никогда `.claude/settings.local.json`, `build/`, `run/`, логи.
- Публикация необратима: загруженные файлы удаляются только вручную на сайте CurseForge. Поэтому номер и текст - строго по правилам 1 и 2, а дальше без лишних вопросов.

## Подготовка

1. `gradle.properties`: `mod_version` - номер пользователя ровно в его написании. Суффикс `alpha` -> файл alpha, `beta` или `-rc` -> beta, иначе release.
2. `CHANGELOG.md` (только на английском, обычная ASCII-пунктуация - этот текст становится описанием файла на CurseForge): раздел `## [Unreleased]` переименовать в `## [X.Y.Z]`, над ним оставить пустой `## [Unreleased]`. Если пользователь прислал текст раздела - раздел версии должен совпадать с ним слово в слово. Если `[Unreleased]` пуст и текста нет - написать пункты по коммитам с прошлого тега (`git log --oneline v<прошлая>..HEAD`) и показать (правило 2). Русский текст перевести, названия интерфейса брать из `common/lang/en_us.json`.
3. Тега ещё нет: `git tag -l vX.Y.Z`, `git ls-remote --tags origin vX.Y.Z`. Есть - сказать и спросить другой номер. **Стоп.**
4. В `git status` есть отслеживаемые изменения, не относящиеся к релизу, - спросить, включать ли их. **Стоп.** Неотслеживаемые (`.claude/` и т.п.) просто не трогать.

## Публикация (делаешь сам)

```
git add CHANGELOG.md gradle.properties
git -c commit.gpgsign=false commit -q -m "Changed: version X.Y.Z"
git log -1 --format='%an <%ae>%n%B'
git tag vX.Y.Z
git push origin main vX.Y.Z
gh run list --workflow curseforge.yml --limit 1
```

Проверить: автор - пользователь, в сообщении нет атрибуции; в `gh run list` появился run с веткой `vX.Y.Z` (если нет сразу - повторить через несколько секунд). Затем следить за ним в фоне (`gh run watch <id> --exit-status` с `run_in_background`), по завершении разобрать лог (раздел 3) и сообщить итог: сколько файлов загружено, file id, ссылка на run.

Пользователю в ответе: одна строка - что тег запушен и run идёт (ссылка `gh run view <id> --web` или URL), и что сообщишь итог.

Пробный прогон - только если пользователь попросил: запушить `main` и `gh workflow run curseforge.yml -f ref=main -f dry_run=true`, норма `Dry run OK: N files`.

## 3. Разбор лога (делаешь сам)

Пока шаг идёт, его лог через API недоступен. Сборка с нуля занимает 18-20 минут; до 45 минут на шаге Build all versions - это не зависание. Ссылка для браузера: `gh run view <id> --web`.

```
gh run list --workflow curseforge.yml --limit 3
J=$(gh run view <run-id> --json jobs --jq '.jobs[0].databaseId')
gh api repos/Grihail/mine-papers-online/actions/jobs/$J --jq '.steps[]|"\(.name) \(.status) \(.conclusion)"'
gh api repos/Grihail/mine-papers-online/actions/jobs/$J/logs --allow-escape-sequences | sed -E 's/\x1b\[[0-9;]*m//g' > "<scratchpad>/run.log"
grep -n -E "BUILD|What went wrong|Execution failed|Caused by|^ERROR:|WARNING: (tag|CHANGELOG|CURSE)|uploaded|FAILED|Uploaded|Dry run|retrying" "<scratchpad>/run.log"
```

Лог сохранять в scratchpad, не в проект. Bash-команды выше - для инструмента Bash, не для пользователя.

Что считать нормой:
- Пробный прогон: `Dry run OK: 12 files` (число = число целей). `WARNING: tag 'main' does not match` при запуске с `ref=main` - ожидаемо.
- Публикация: по строке `uploaded, file id ...` на файл и `Uploaded N files`.
- Строки Gradle `WARNING: ... is not present in the artifact manifest` - шум плагинов Forge/NeoForge.

## 4. Если что-то пошло не так

- **Часть файлов не загрузилась.** Скрипт в конце пишет значение `only`. Запустить самому (обычный Re-run не делать: он загрузит все файлы повторно):
  ```
  gh workflow run curseforge.yml -f ref=vX.Y.Z -f dry_run=false -f only=26.2-forge,26.3-neoforge
  ```
- **Проверка не прошла, ничего не загружено** (не тот тег, нет раздела CHANGELOG): исправить, закоммитить и переставить тег самому:
  ```
  git tag -d vX.Y.Z
  git push origin :refs/tags/vX.Y.Z
  git tag vX.Y.Z
  git push origin main vX.Y.Z
  ```
  Переставлять тег только если в логе нет ни одной строки `uploaded`.
- **`CurseForge has no game version '...'`**: CurseForge ещё не добавил эту версию Minecraft. Ждать, пока добавит, или выпустить без этой цели через ручной запуск с `only`.
- **`shrinkWebp` падает с `jmods/java.base.jmod`**: ProGuard нужна папка `jmods`. В Temurin 24+ её нет, поэтому JDK 25 в workflow - `distribution: oracle`, и Gradle запущен с `org.gradle.java.installations.auto-detect=false`. Не менять обратно.
- **Новая цель (версия игры или загрузчик)**: скрипт находит цели сам по `modern/versions/*` и `<версия>/<загрузчик>`. Если ей нужна новая мажорная Java, добавить её в шаг `setup-java` и в `-Porg.gradle.java.installations.fromEnv`. Новый загрузчик - добавить в `LOADERS` скрипта. Fabric-файлы автоматически получают обязательную зависимость `fabric-api`.

## Что получается на CurseForge

- Имя файла: `<версия игры>-<загрузчик>-<версия мода>`, например `26.3-neoforge-1.6.1`.
- Версии игры: номер Minecraft, загрузчик, `Client`, `Server`.
- Описание: раздел версии из `CHANGELOG.md` (markdown).
- Файлы нового релиза сначала проходят модерацию CurseForge и появляются на странице мода не сразу. Статус - в https://authors.curseforge.com/ -> проект -> Files.
